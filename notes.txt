Complexity Ranking => Best to worst:
  O(1)     => Constant     => Peek at the root of a binary heap
  O(logn)  => Logarithmic  => Insert into a binary heap
  O(n)     => Linear       => Scan an array
  O(nlogn) => Linearithmic => Efficient comparison-based sorting
  O(n^2)   => Quadratic    => Nested loops over an array

Dynamic Programming:
  The basic thing which I know about Dynamic Programming is that we solve smaller problems and then combine them into a larger solution.
  There are techniques to Dynamic Programming like - Memoization, Tabulation, Grid, Constant & Non Constant Transitions, 2 sequences, Knapsack, etc.
  In DP, avoid repeated calculations of already computed steps. We tackle that by storing the already computed results somewhere using memoization. The next thing is that we use recusrion a lot in DP problems. We generally use Hashmap for storing the memoized values. We only perform computations when there's no value found for the corresponding calculation in the memoized data. We have to maintain base cases for the recursion to stop at some point. It's very similar to the read through strategy we use in Redis storage for system design for frequently accessed, derived expensive data. Memoization is recursion with memory.

  Recursion breaks a problem into smaller subproblems.
  Memoization avoids solving the same subproblem repeatedly.
  Dynamic programming is an approach for solving problems with overlapping subproblems and optimal substructure; it can use memoization (top-down) or tabulation (bottom-up).
  Whenever we need to find the optimum solution out of the many possible options. DP is a good option. Such as the KnapSack problem or Min Cost Climbing Stairs problem or even find how many paths to a cell from a grid.

Compilation Steps:
  GCC - Stands for GNU Compiler Collection. It has compilers for C, C++, Objective C & even Go.
  Thus we can even compile Golang code from GCC, not only the native Go compiler.
  We compile different languages using:
    gcc => C
    g++ => C++
    gfortran => Fortran
    gccgo => Go

  When we compile using GCC, it goes through 4 steps.
  Steps:
    Pre-processor -> Compiler -> Assembler -> Linker

  The compilation begins. It first compiles into assembly language, then into machine code.
  Assembler is also a compiler and it does the job of the compilation to machine from assembly. The result is the `.o` or the object file. But that's not the final output.
  The Linker then is responsible for linking all the preprocessor directives and external libraries to the object file.
  The linking can be done with Static and Dynamic Linking. In Static Linking, we combine everything into a single executable. But in Dynamic Linking, we have the `.dll` - Dynamically Linked List files on Windows and `.so` - Shared Object files on Unix Systems. As we saw in windows systems when we used to play games. The produced `.dll` or `.so` files have got executable code with the functions exposed from the file to be included in our main source code. The execution of those functions happens directly from those files only. It's like microservices where each .so file can be compiled from a different source code files and then be used independently by other programs.
  Because with dynamic linking, what we do is that we just link the code from external libraries to our main executable file. That reduces repeated machine code in our final executable when same libraries are references multiple times thus saving disk space and reducing the bloat of the final executable.
  The linker then combines them and produces a executable file.
  The compilers hides all of these steps by default. We can get the code of all the steps:
    gcc ./multi_os.c -o main -save-temps
  With this we get multi_os.i, multi_os.o, multi_os.s, multi_os.bc files.
  Each of these files showing up steps linked:
    .i => Preprocessed C source => Preprocessing Step, contains readable code
    .s => Assembly text => Compilation Step, contains readable code
    .o => Object code and metadata => Assembly Step
    .bc => LLVM intermediate representation => LLVM-specific workflow Step
    Final => Linked Executable
  This is incredibly useful when we want to get to know what's going on underneath the hood. It also helps to debug performance critical code.

  We can even combine code from assembly files with `.s` extensions and then produce a workable output. Here we can see multiple files compiling in action:
    Producing separate output files from all the compilation steps:
      gcc ./calc_funcs.c -o main -save-temps
    Compiling from multiple files. One file is the assembly code output from above step, the next is the source code file which uses that assembly code, which is combined to a single executable file:
      gcc ./calc_funcs.s ./main.c -o main
    Finally we produce a single `main` executable file.
  We can similarly compile programs from different languages into assembly and then link those assembly files into a single executable. Linker does the job of linking the assembly codes into the executable. It doesn't matter if the code has come from a different compilation chain altogether. So, we can compile in Go's native compiler generate the assembly and then link it with C's assembly and produce final executable.
  We generally mix up multiple languages in a single project for performance reasons or not reinventing the wheel of if some library is already developed in other language, we can just use it for us.
  Thus we mostly use up C/C++ in Rust code or even in Python code just like we have pandas & numpy using up C for performance critical calculations and using Python only as programming interface.
  Even that is not all Disneyland. There might arise compatibility problems later on when assemblers of different languages aren't exactly compatible or produce different results when interacting with the hardware.
  But anyways, this is Revolutionary! A step forward in my engineering knowledge.

Recall that why do we need to set PATH variables?
  We need to set PATH variables for Java, Python, Golang, Node or PHP and even for Android emulators and SDKs.
  The reason being that the terminal/shell fetches the paths of the executables when it encounters unknown commands in the terminal, if it knows the path then it will call the appropriate executable else throw an unknown command error. We thus actually provide the absolute paths of the executables related to those programming languages or tools in order for them to call the necessary executables.
  When we run interpreted languages we call the interpreter which is actually an executable file or binary!
  The terminal searches the path to the interpreter's binary and then passes on the source files of the programs to execute as arguments to the interpreter. Just like we pass in for Python or Node or others as well.
  The shell launches the Python executable and passes Python file as an argument. The Python runtime processes the source code, typically compiling it to bytecode internally before execution.
  The source file is loaded onto the heap memory and then converted to machine code an then finally executed.
